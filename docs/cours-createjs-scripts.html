CreateJS dans les scripts TweenJS

Comment la bibliothèque CreateJS a été intégrée de A à Z dans le panneau Scripts de ton éditeur — et comment toi, tu peux faire pareil. Un cours de terrain : chaque concept est illustré par du code réel du projet.

Niveau : intermédiaireJS vanillaSession du 02/10/2026

0.La carte du territoire

Avant d'épluder le code, garde en tête le voyage complet d'un clic sur le bouton Exécuter :

index.html                 -- 4 <script> UMD chargent createjs sur la globale window.createjs
  |
  v
public/libs/createjs/*.min.js   -- EaselJS, TweenJS, SoundJS, PreloadJS (MIT)
  |
  v
src/main.js                -- crée le stage, l'état, puis le runtime :
  |                           createSceneRuntime({ state, stageContainer, toScenePoint })
  v
src/runtime/sceneRuntime.js -- compile et exécute TON script
  |
  v
new Function('Scene','Game','console','named','createjs', ...tonCode)
                            -- ton code tourne avec 5 paramètres

Trois idées force le dispositif :

  1. Le script utilisateur est une fonction, pas un fichier. On ne l'évalue pas « dans » l'application : on le compile avec new Function et on lui passe tout ce qu'il a le droit de voir.
  2. CreateJS n'est pas modifié ni réécrit. C'est la vraie bibliothèque, chargée comme n'importe quelle page web la chargerait. On se contente de la rendre visible dans la sandbox du script.
  3. Rien ne fuit dans le document. Les éléments nommés reçoivent des méthodes d'événements, mais le document sauvegardé en JSON reste strictement identique (on verra l'astuce).

1.Comment naît et meurt un script

Fichier étudié : src/runtime/sceneRuntime.js

Quand tu cliques Exécuter dans le panneau Scripts, le panneau appelle runtime.run(code). Voici ce qui se passe réellement, sans raccourci :

// sceneRuntime.js (simplifié pour lire, fidèle pour comprendre)
function run(code, consoleCb) {
  onConsole = consoleCb;               // la console du panneau capte console.log
  enterFrameCbs.clear();               // on vide TOUTES les inscriptions
  keyDownCbs.clear();
  keyUpCbs.clear();
  clickCbs.clear();
  execCode(code);                      // ...puis on exécute une seule fois
  return Scene;
}

Leçon de conception n°1 : vider avant d'exécuter

Chaque run repart de zéro. Sans ça, chaque exécution empilerait des doublons : deux onEnterFrame, deux onKeyDown... et ton animation accélérerait à chaque Exécuter. Un runtime de script doit être idempotent : rejouer ne change pas le résultat.

Le cœur : execCode

function execCode(code) {
  const named = namedNow();              // instances nommées de l'image courante
  detachAllEvents(Scene);                 // nettoyage des handlers d'événements
  for (const el of Object.values(named)) detachAllEvents(el);
  const prelude = namedVarNames(named)
    .map((n) => `var ${n} = named[${JSON.stringify(n)}];`)   // voir partie 2
    .join('\n');
  const fn = new Function(
    'Scene', 'Game', 'console', 'named', ...SCRIPT_LIBS,     // 'createjs'
    '"use strict";\n' + prelude + '\n' + code);
  fn(Scene, Scene, proxyConsole, named, ...scriptLibValues());
}

Deux choses à méditer :

  • "use strict" est mis en première ligne. Conséquence directe : this vaut undefined au niveau supérieur du script. C'est exactement pour ça que ton premier essai this.tst.on("click", ...) plantait : en mode strict, un script n'a pas de « soi ». Les variables sont les seuls points d'entrée.
  • Toute la sécurité est dans la liste des paramètres. Le script ne voit pas l'application ; il voit cinq paramètres : Scene, Game (alias), console, named, createjs. Tu veux donner autre chose à un script ? Tu l'ajoutes à cette liste. C'est le contrat, noir sur blanc.

Pourquoi new Function et pas eval ?

eval s'exécute dans la portée ambiante : le script verrait les variables internes du runtime (et l'inverse : tes variables pourraient être écrasées). new Function crée une fonction dont la seule portée englobante est la portée globale. Tout ce que le script touche doit donc lui être donné explicitement. On fabrique une frontière au lieu de laisser une porte ouverte.

2.Les instances nommées : de la donnée à la variable

Fichiers étudiés : src/core/model.js (getNamedElements), sceneRuntime.js

Dans l'éditeur, un élément posé sur la scène n'est pas un objet graphique : c'est une donnée — un objet JavaScript simple, sérialisable en JSON, qui décrit la forme (x, y, width, fill, points...). Konva, lui, ne fait que dessiner cette donnée.

// model.js — le nom devient une clé de map
export function getNamedElements(doc, editPath, frameIndex) {
  const layers = getContextLayers(doc, editPath);
  const out = {};
  for (const layer of layers) {
    const kf = getActiveKeyframe(layer, frameIndex);
    if (!kf) continue;
    for (const el of kf.elements) {
      const name = (el.name || '').trim();
      if (name) out[name] = el;      // <-- la référence VIVE de l'élément
    }
  }
  return out;
}

Ensuite, execCode fabrique un prélude : quelques lignes de déclaration collées devant ton code :

// ce que reçoit vraiment ton script, par exemple :
var tst = named["tst"];
var circ = named["circ"];
"use strict";
// ...ton code, ici...

C'est pour ça que tst.x += 1 fonctionne sans import ni déclaration : la variable existe avant ta première ligne. Et comme c'est la référence vive (pas une copie), modifier tst.x modifie le document — le rendu suit.

Le piège des mots réservés

Que se passe-t-il si tu nommes une instance class, this ou new ? Le prélude deviendrait var class = ... : erreur de syntaxe, script mort. Le runtime maintient donc une liste RESERVED et exclut ces noms de l'injection. L'instance reste accessible par la porte de secours : named["class"]. Retiens le réflexe : toute génération de code par code doit se demander « et si la donnée contient un truc illégal ? »

function namedVarNames(named) {
  return Object.keys(named)
    .filter((n) => /^[A-Za-z_$][A-Za-z0-9_$]*$/.test(n) && !RESERVED.has(n));
}

3.Charger CreateJS en local, pour de vrai

Fichiers étudiés : index.html, public/libs/createjs/

CreateJS est un ensemble de quatre bibliothèques MIT, historiquement livrées en fichiers UMD : un seul fichier JavaScript qui s'installe sur une variable globale, ici createjs. Ouvre easeljs.min.js et regarde le tout début :

this.createjs = this.createjs || {}, ...

Traduction : « mets-toi sur la globale createjs, en la créant si elle n'existe pas ». Les quatre fichiers s'empilent sur la même globale : createjs.Event (EaselJS), createjs.Tween (TweenJS), createjs.Sound (SoundJS), createjs.LoadQueue (PreloadJS).

Le chargement

<!-- index.html, avant le module de l'application -->
<script src="/libs/createjs/easeljs.min.js"></script>
<script src="/libs/createjs/tweenjs.min.js"></script>
<script src="/libs/createjs/soundjs.min.js"></script>
<script src="/libs/createjs/preloadjs.min.js"></script>

Deux détails qui comptent :

  • L'ordre est significatif. Les balises script classiques (sans type="module") s'exécutent dans l'ordre du document. TweenJS s'attend à trouver le createjs d'EaselJS déjà là. Respecter les dépendances d'une pile de bibliothèques est une compétence à part entière : quand ça casse, pense ordre avant tout.
  • Pourquoi public/ ? Vite sert le contenu de public/ à la racine en dev et le copie tel quel dans dist/ au build. Un seul rangement, deux environnements.

Leçon de terrain : les versions disponibles ne sont pas celles du site

Sur npm, SoundJS et PreloadJS s'arrêtent à 1.0.1 alors qu'EaselJS/TweenJS sont en 1.0.2. Toujours vérifier ce qui existe réellement dans le canal de distribution que tu utilises, au lieu de supposer que tout est aligné. Et toujours garder les fichiers LICENSE à côté des .min.js : c'est une exigence de la MIT et un bon réflexe professionnel.

4.Le mécanisme d'injection : trois lignes extensibles

Fichier étudié : sceneRuntime.js (haut du fichier)

Voici tout le mécanisme qui rend createjs disponible dans les scripts — il tient en trois lignes :

const SCRIPT_LIBS = ['createjs'];

function scriptLibValues() {
  return SCRIPT_LIBS.map((name) =>
    (typeof globalThis[name] === 'undefined' ? undefined : globalThis[name]));
}

et il est branché aux deux endroits où un code utilisateur est compilé :

const fn = new Function('Scene', 'Game', 'console', 'named', ...SCRIPT_LIBS, ...);
fn(Scene, Scene, proxyConsole, named, ...scriptLibValues());

Regarde bien la symétrie : SCRIPT_LIBS sert deux fois — une fois comme noms de paramètres de la fonction compilée, une fois comme valeurs passées à l'appel. Ajouter une bibliothèque demain, c'est ajouter un mot dans ce tableau. Rien d'autre ne change : ni RESERVED (il est construit avec ...SCRIPT_LIBS dedans), ni la signature, ni l'appel.

Leçon de conception n°2 : le registre plutôt que le cas particulier

La version naïve aurait été : new Function('Scene', ..., 'createjs', ...) codée en dur. Ça marche... une fois. La version registre transforme « un cas » en « une catégorie ». C'est le mécanisme qui réalisera ta demande de pouvoir charger n'importe quelle bibliothèque : charger le fichier, ajouter le nom de sa globale dans SCRIPT_LIBS, finito.

Pourquoi globalThis et pas window ?

globalThis désigne l'objet global quel que soit l'environnement : window dans un navigateur, global dans Node. Grâce à ça, le même fichier sceneRuntime.js tourne dans l'application et dans le harnais de test Node (voir partie 10). Chaque fois que tu écris « l'environnement », demande-toi si window est vraiment ce que tu veux dire.

5.Le système d'événements : recevoir des méthodes sans salir la donnée

Fichier étudié : sceneRuntime.js (bloc EVENT_HANDLERS)

Objectif : que tst.on("click", fn) fonctionne, avec la sémantique d'EaselJS, sur des objets qui sont... de la donnée JSON. Le défi : ajouter des méthodes à un objet sans qu'elles apparaissent dans le document sauvegardé. Deux outils font tout le travail :

OutilRôle
WeakMapLes handlers sont rangés dans une map à côté des éléments, pas dedans. La donnée reste pure.
Object.defineProperty
(enumerable: false)		Les méthodes (on, off, dispatchEvent...) sont posées sur l'élément mais non énumérables. JSON.stringify, Object.keys et le panneau Propriétés ne les voient jamais.
const EVENT_HANDLERS = new WeakMap();  // élément -> Map(type -> Set de handlers)

function attachEventApi(obj) {
  if (obj.__hasEventApi) return obj;
  const methods = { on: ..., off: ..., dispatchEvent: ... };
  for (const name in methods) {
    Object.defineProperty(obj, name, {
      value: methods[name], enumerable: false, configurable: true
    });
  }
  ...
  return obj;
}

Un WeakMap (map « faible ») ne retient pas fortement son contenu : quand un élément disparaît du document, son entrée peut être ramassée par le ramasse-miettes. Pas de fuite mémoire, pas de nettoyage manuel. Retiens cette alliance : WeakMap pour les données annexes, defineProperty non-énumérable pour les méthodes — c'est un pattern réutilisable dès que tu dois « habiller » des données qui ne t'appartiennent pas.

L'API obtenue (sémantique EaselJS)

MéthodeComportement
el.on(type, fn) (alias addEventListener)Inscrit un handler ; renvoie un wrapper utilisable dans off.
el.off(type, fn|wrapper) (alias removeEventListener)Désinscrit par handler d'origine ou par wrapper renvoyé par on.
el.removeAllEventListeners(type?)Tout (ou tout un type).
el.hasEventListener(type)Interrogation.
el.dispatchEvent(evt|string)Déclenche à la main ; remplit target si absent.

Le pipeline pointeur

Les événements souris ne tombent pas du ciel : le runtime pose quatre écouteurs DOM sur le conteneur du stage (mousedown, mousemove, mouseup, dblclick) et traduit chaque geste :

mousedown  --> hit-test  --> el.dispatchEvent("mousedown")   + Scene "stagemousedown"
mousemove  --> si pressé : "pressmove" sur l'élément pressé
               si survol change : "rollout"+"mouseout" sur l'ancien,
                                   "rollover"+"mouseover" sur le nouveau
mouseup    --> "mouseup" sur la cible, "pressup" sur l'élément pressé,
               "click" SI ET SEULEMENT SI down et up sur le même élément

La règle du clic EaselJS est fidèle : un click = down et up sur le même objet. Clique un carré, relâche à côté : pas de click. C'est le comportement auquel s'attendent tous les gens qui viennent de CreateJS — être compatible, c'est d'abord respecter les règles subtiles, pas juste les noms de fonctions.

Pourquoi rien ne se déclenche hors lecture ?

En édition, un clic sur la scène appartient aux outils (sélection, dessin). Si les scripts pouvaient aussi réagir, tu aurais des alertes au milieu d'un tracé de plume. Le runtime applique donc une règle simple et documentée : les événements de script ne vivent que pendant la lecture, exactement comme les scripts d'image. Devant chaque ressource partagée, pose-toi la question : « à qui appartient ce clic ? »

6.TweenJS et l'horloge : deux temps, un seul bouton pause

Fichier étudié : src/main.js (boucle loop)

Problème délicat de l'intégration : createjs.Tween avance sur sa propre horloge (le Ticker de CreateJS, typiquement à 60 Hz via requestAnimationFrame), alors que l'éditeur avance à la cadence du document (24 images/s par défaut). Si on ne fait rien, deux bugs d'expérience :

  • tu mets l'éditeur sur pause... et les tweens continuent en coulisses ;
  • les tweens avancent à 60 Hz mais la scène ne se redessine qu'à chaque image de timeline (24 Hz) : animation saccadée.

Deux réglages, dans la boucle loop() de main.js :

// 1. Le Ticker CreateJS respire avec l'éditeur
const createjs = globalThis.createjs;
if (createjs && createjs.Ticker) createjs.Ticker.paused = !state.playing;

// 2. Pendant la lecture, on redessine à CHAQUE frame d'affichage,
//    pas seulement à chaque image de timeline
stage.render(tick);   // en fin de loop(), exécuté à ~60 Hz

Ticker.paused est une propriété documentée de CreateJS 1.0 : le tick continue d'être émis, mais marqué paused: true, et les tweens l'ignorent. Résultat : un seul bouton pause pilote les deux mondes. Cherche toujours le point de synchronisation entre deux systèmes qui ont chacun leur horloge — c'est presque toujours là que se cache le bug.

7.Le hit-testing : des maths simples, bien rangées

Fichier étudié : sceneRuntime.js (hitTestElement)

Pour savoir si ton clic touche tst, il faut ramener le point du repère scène vers le repère local de l'élément (position, rotation, échelle inversées), puis tester selon le type de forme :

function hitTestElement(el, px, py, doc) {
  const dx = px - (el.x || 0), dy = py - (el.y || 0);
  const rot = -(el.rotation || 0) * Math.PI / 180;   // degrés -> radians, signe inversé
  const cos = Math.cos(rot), sin = Math.sin(rot);
  const lx = dx * cos - dy * sin;                  // rotation inverse appliquée
  const ly = dx * sin + dy * cos;
  const sx = el.scaleX == null ? 1 : el.scaleX;
  const sy = el.scaleY == null ? 1 : el.scaleY;
  if (el.shapeType === 'ellipse') {
    // test de disque : (lx/rx)² + (ly/ry)² <= 1
  }
  // lignes/chemins : boîte englobante des points
  // instances : hull du symbole (partie 9) ; le reste : boîte englobante
}

Trois choix pédagogiques dans cette fonction :

  1. Ellipse = test de disque, pas de boîte. Le facile aurait été une boîte englobante pour tout. Le joueur qui clique dans un coin vide d'une ellipse ronde ne doit pas être récompensé.
  2. el.x || 0 partout. La donnée vient d'un document utilisateur : des champs peuvent manquer. Chaque accès est défensif — (el.x || 0), (el.scaleX == null ? 1 : el.scaleX). Ton code doit survivre aux données imparfaites.
  3. Les instances sont le cas dur. Une instance n'a pas de largeur : sa taille est celle du symbole qu'elle référencie. Solution : calculer l'enveloppe (hull) de tout ce que le symbole dessine, sur toutes ses images, récursivement.

8.Recettes pratiques : ton tour de jouer

Toutes ces recettes s'écrivent dans le panneau Scripts, au niveau supérieur du script (jamais dans onEnterFrame — voir la règle d'or ci-dessous).

La règle d'or des handlers

Les inscriptions d'événements se font une fois, au top-level du script. Un tst.on("click", ...) écrit dans onEnterFrame serait réexécuté à chaque image et empilerait les handlers. Le runtime nettoie tout à chaque Exécuter précisément pour que tu puisses réessayer tranquillement — profites-en, mais écris les inscriptions au bon endroit.

Recette 1 — Clic sur une instance nommée

Scene.play();   // les événements ne vivent qu'en lecture
tst.on("click", function (ev) {
  Scene.log("clic en", ev.stageX, ev.stageY, "sur", ev.target.name);
});

Recette 2 — Tween de base (la façon CreateJS)

Scene.play();
createjs.Tween.get(tst)                       // cible : l'élément nommé
  .to({ x: 400, rotation: 180 }, 1000)        // 1 seconde, easing linéaire par défaut
  .wait(300)                                 // pause de 300 ms
  .to({ y: 300 }, 500, createjs.Ease.bounceOut);  // avec rebond

createjs.Ease est le catalogue de courbes d'accélération (linear, quadOut, bounceOut, elasticOut...) : on passe la fonction voulue en 3e paramètre de to(). Sans paramètre, l'interpolation est linéaire.

Recette 3 — Glisser-déposer à la EaselJS

Scene.play();
tst.on("mousedown", function (ev) { tst._drag = true; });
tst.on("pressmove", function (ev) {
  if (!tst._drag) return;
  tst.x = ev.stageX;   // au centre ; pour un déplacement relatif,
  tst.y = ev.stageY;   // garde le delta à mousedown et soustrais-le
});
tst.on("pressup", function () { tst._drag = false; });

Attention : tst._drag s'écrit dans la donnée de l'élément et finira dans le document sauvegardé. Pour un état vraiment éphémère, utilise une variable du script (fermeture) plutôt que l'élément.

Recette 4 — Ticker : sa propre cadence

Scene.play();
let t = 0;
createjs.Ticker.addEventListener("tick", function (e) {
  t += e.delta / 1000;                 // delta en ms -> secondes
  circ.x = 300 + Math.sin(t * 3) * 50; // orbite douce
});
// e.paused vaut true quand l'éditeur est en pause : le callback
// reçoit toujours le tick, à toi de respecter e.paused si tu le veux strict

Recette 5 — Scene-level : tout clic, même dans le vide

Scene.play();
Scene.onClick(function (x, y) {            // API de l'éditeur
  Scene.log("clic scène à", x, y);
});
Scene.on("stageclick", function (ev) {      // forme EaselJS, équivalent
  Scene.log("stageclick", ev.stageX, ev.stageY);
});
Scene.onClick("tst", function (x, y, el) {   // ciblé par nom
  el.rotation += 15;
});

9.L'export HTML : embarquer CreateJS proprement

Fichier étudié : src/export/exportHTML.js

« Exporter HTML » génère un fichier autonome : il doit marcher hors ligne, sans le dossier public/. Deux contraintes opposées :

  • si un script utilise createjs, l'export doit contenir la bibliothèque (~280 Ko) ;
  • sinon, les coller partout gonflerait chaque export de 280 Ko de code mort.

La solution est un chargement conditionnel :

function collectAllScripts(doc) { ... }   // scripts nommés + scripts d'image
                                          // (racine + tous les symboles)
if (collectAllScripts(doc).some((code) => /\bcreatejs\b/.test(code))) {
  libScripts = (await loadCreateJsSources())       // fetch des 4 .min.js
    .map((src) => '<script>\n' + src + '\n</script>\n')
    .join('');
}
// puis, dans le HTML final :
// <canvas id="stage"></canvas>
// ${libScripts}<script type="module">...bootstrap...</script>

Et dans le bootstrap exporté, chaque new Function reçoit le paramètre createjs protégé par une garde :

var fn = new Function('Scene','Game','console','named','createjs', ...);
fn(Scene, Scene, console, named,
   (typeof createjs !== 'undefined' ? createjs : undefined));

La garde typeof est le seul moyen en JavaScript de tester une variable peut-être non déclarée sans lancer de ReferenceError. Si les libs manquent, le script ne crashe pas au chargement : createjs vaut undefined et l'erreur, si erreur il y a, pointera la ligne de l'utilisateur.

Le détail qui tue les exports : </script>

Inliner du JavaScript dans un bloc <script> d'un fichier HTML est sûr sauf si la source contient la séquence </script> (qui fermerait le bloc prématurément) ou <!--. On l'a vérifié sur les quatre fichiers avant de s'autoriser l'inlining direct. Quand tu colles du code dans du code, liste toujours les séquences qui cassent l'enveloppe et vérifie-les.

10.La technique de travail : comment on arrive au résultat

Le code, tu viens de le lire. Ce qui fait la différence, c'est la méthode autour. Voici les habitudes que j'ai appliquées sur cette intégration — ce sont elles que je te propose de faire tiennes.

  1. Lire avant d'écrire. Avant la moindre modification, j'ai lu sceneRuntime.js, main.js (la boucle), exportHTML.js et cherché ce qui existait déjà (pointFromClient, getNamedElements). Réutiliser une fonction existante vaut mieux qu'en écrire une neuve.
  2. Changer peu, garder le style. Le diff final touche six fichiers et s'aligne sur les conventions du projet (commentaires français explicatifs, même style d'indentation). Modifier le minimum n'est pas de la paresse : c'est de la réduction de surface de risque.
  3. Prouver, pas croire. Un harnais Node (_wrk_mistral_mem/repro_createjs.mjs) charge les vraies bibliothèques dans une sandbox node:vm et vérifie 21 comportements : tween réel, clics, hit-tests, absence d'empilement, sérialisation intacte. « Ça marche » n'existe pas tant que rien ne l'a observé.
  4. Se méfier des couches d'échappement. Un outil d'édition doublait les backslashes : le gabarit de script s'est retrouvé cassé par l'instance (une apostrophe fermait la chaîne) et par \\n. La loi : après toute écriture contenant des backslashes, on relit les octets (tr '\\' '#', od -c), pas l'affichage. L'affichage ment ; les octets non.
  5. Quand un test échoue, suspecter le test d'abord. Sur 21 contrôles, les 2 échecs venaient du harnais lui-même (un point de clic « hors ellipse » placé en réalité dedans ; un survol déjà actif). Le réflexe : recalculer l'hypothèse du test avant d'accuser le code.
  6. Écrire pour le prochain lecteur. Chaque décision non évidente est un commentaire de pourquoi dans le code (WeakMap non-énumérable, Ticker.paused, garde typeof). Le code dit ce qui ; les commentaires disent pourquoi.
  7. Tenir un journal. Le dossier _wrk_mistral_mem/ archive chaque session : ce qui a été fait, ce qui reste, les pièges rencontrés. Une mémoire écrite vaut dix souvenirs.

11.Exercices

À faire dans ton éditeur : ouvre un projet, nomme une instance (champ « Nom d'instance » dans les propriétés), ouvre le panneau Scripts, et mets la lecture. Les corrigés sont repliés : cherche d'abord seul, c'est là que ça s'apprend.

Exercice 1 — Le phare

Fais tourner un rectangle nommé lampe en continu sur lui-même, de deux façons : (a) uniquement avec l'API Scene, (b) uniquement avec createjs.Tween. Puis fais-le s'arrêter quand on clique dessus, et repartir quand on clique sur la scène (dans le vide).

Corrigé 
Scene.play();
// (a) API Scene
Scene.onEnterFrame(() => { lampe.rotation = (lampe.rotation + 3) % 360; });
// (b) Tween : tourner indéfiniment = tween court + appel à on complete
function tourne() {
  createjs.Tween.get(lampe).to({ rotation: 360 }, 1000)
    .call(() => { lampe.rotation = 0; tourne(); });
}
tourne();
// stop / reprise
lampe.on("click", ()  => { createjs.Tween.removeTweens(lampe); });
Scene.onClick((x, y) => { if (!hitLampe(x, y)) tourne(); });

Remarque : Scene.onClick « dans le vide » peut aussi se filtrer en comparant au hit de lampe via l'événement stageclick + les coordonnées.

Exercice 2 — Drag propre

Améliore la recette 3 : le déplacement doit être relatif (l'élément ne saute pas au centre du curseur), et l'élément ne doit jamais sortir des limites de la scène (Scene.width, Scene.height).

Corrigé 
Scene.play();
