CreateJS dans TweenJS — v2 : le système complet

La v1 t'a appris les fondations (new Function, injection, UMD, WeakMap). La v2 va plus loin : le registre à portées, le pipeline pointeur, la parité éditeur/export — expliqués sur le bug réel qui les a fait naître. Prérequis : cours-createjs-scripts.html (v1).

Niveau : intermédiaire+Session du 03/10/2026Basé sur un bug réel

0.Ce que la v2 ajoute

Trois choses ont changé depuis la v1, et chacune est née d'un problème concret :

NouveautéProblème qui l'a rendue nécessaire
Registre d'événements à portées (run / frame / null)Un script d'image purgeait les handlers posés par le bouton Exécuter — le clic d'un bouton devenait muet 80 ms après le lancement.
Pipeline pointeur dans l'export HTMLL'export ne répondait pas aux clics : le bootstrap ne connaissait que le clavier et onEnterFrame.
gotoAndPlay/gotoAndStop avec labels dans l'éditeurScene.gotoAndStop("Start") ne fonctionnait que dans l'export.

1.Le contrat d'un script (rappel actif)

Rappel de la v1, à connaître par cœur

Un script est compilé par new Function et reçoit cinq paramètres : Scene, Game (alias), console, named (map des instances nommées de l'image courante), createjs (la bibliothèque complète). Mode strict : this vaut undefined au niveau supérieur. Les instances nommées sont injectées comme variables directes par un prélude généré (var But = named["But"];).

Le réflexe v2 : quand quelque chose ne marche pas, interroge le contrat plutôt que deviner :

Scene.log("createjs :", typeof createjs);              // la lib est-elle là ?
Scene.log("nommes :", Object.keys(named).join(", ") || "AUCUN"); // qui est visible ?
Scene.log("But typeof:", typeof But);                  // l'injection a-t-elle eu lieu ?
Scene.log("playing:", Scene.playing);                      // la lecture tourne-t-elle ?

Ce quadri-diagnostic élimine 90 % des hypothèses en quatre lignes. C'est lui qui a orienté toute l'enquête de la partie 7.

2.Le registre à portées : qui possède un handler ?

Fichier étudié : src/runtime/sceneRuntime.js (bloc EVENT_HANDLERS)

Le problème des purges

Deux sorties de scripts partagent le même moteur (execCode) :

  • les scripts du document (panneau Scripts, bouton Exécuter) — rejouables à volonté ;
  • les scripts d'image (posés sur une image clé d'un calque) — rejoués automatiquement à chaque passage de la tête de lecture sur l'image.

Si on purge tous les handlers avant chaque exécution (pour éviter l'empilement), les scripts d'image effacent les handlers du bouton Exécuter. Si on ne purge jamais, chaque passage d'un script d'image empile un handler de plus. Les deux moitiés du dilemme sont mauvaises — la solution est de demander : à qui appartient ce handler ?

La solution : un owner sur chaque handler

// Chaque handler porte une PORTEE d'enregistrement :
//  'run'   -> posé pendant le bouton Exécuter (script du document)
//  'frame' -> posé pendant un script d'image
//  null    -> posé en dehors de toute exécution (ex : dans onEnterFrame)
let CURRENT_HANDLER_REG = null;  // posé autour de l'exécution du script

handlerSet(this, type, true).add({ cb, scope, once, wrapped, owner: CURRENT_HANDLER_REG });
// La purge devient sélective :
detachAllEvents(Scene, reg);              // dans execCode : ne purge que SA portée
// run() fait le reset complet, toutes portées confondues :
detachAllEvents(Scene, null);
for (const el of Object.values(named)) detachAllEvents(el, null);

Conséquence pratique des trois règles :

Tu écris…PortéeVie du handler
But.on("click", fn) au top-level du script, lancé par Exécuterrunvit jusqu'au prochain Exécuter ; survit à tous les scripts d'image
tst.on("click", fn) dans un script d'imageframepurgé au prochain script d'image exécuté — pas d'empilement d'un passage à l'autre
tst.on("tick", fn) à l'intérieur d'un onEnterFramenulljamais purgé automatiquement : anti-pattern — un handler de plus à chaque image

La leçon de conception

Quand une ressource est partagée par plusieurs cycles de vie (ici : les handlers), ne pose pas la question « quand tout purger ? » mais « à qui appartient chaque entrée ? ». Un champ owner coûte une ligne et transforme un dilemme en non-problème. C'est le même principe qui distingue removeEventListener ciblé d'un innerHTML = '' brutal.

3.Le pipeline pointeur : anatomie d'un clic

Fichiers : sceneRuntime.js (éditeur) et exportHTML.js (export — même logique, style ES5)

Un clic sur la scène traverse cinq étapes. C'est en connaissant les cinq que tu peux localiser un silence :

1. DOM        mousedown/mouseup/mousemove/dblclick sur le conteneur (éditeur)
              ou le canvas (export)
2. PORTE      state.playing (éditeur) / root.isPlaying (export) : hors lecture,
              RIEN ne passe — en édition, le clic appartient aux outils
3. COORDONNEES ecran -> scene : pointFromClient (inverse zoom/pan Konva)
              ou canvas.width/rect.width (export, tolerant au redimensionnement CSS)
4. HIT-TEST   element le plus HAUT sous le curseur parmi les nommes de l'image
5. DISPATCH   evenements EaselJS + Scene-level + Scene.onClick

La sémantique EaselJS, fidèlement

ÉvénementÉmis quand
mousedown / mouseupSur l'élément sous le curseur au moment de l'événement.
clickSeulement si down et up sur le même élément. Presse le bouton, relâche à côté : pas de click. C'est la règle CreateJS, pas un caprice.
pressmove / pressupSur l'élément pressé, pendant/après la pression — même si le curseur en est sorti. C'est ce qui rend le glisser-déposer possible.
mouseover/mouseoutChaque changement de cible survolée.
rollover/rolloutIdem, sémantique « entrée/sortie propre » — sur des objets plats, identiques à mouseover/out.
dblclick / tickDouble-clic sur l'élément ; tick émis à chaque image de lecture (sur les nommés et Scene).
stagemousedown / stagemousemove / stagemouseup / stageclickSur Scene, pour TOUT clic/mouvement — même dans le vide.

L'état de pression, le détail qui tue

Le pipeline mémorise pressTarget au mousedown pour le comparer au mouseup et émettre click. Cet état ne doit jamais être réinitialisé par un script d'image : à 12 fps, une pression de 100 ms traverse au moins une image — réinitialiser pressTarget entre-temps tuerait tout clic. C'est exactement le piège qui a été corrigé en même temps que les portées : le reset vit désormais dans run() uniquement.

4.Le hit-testing en questions

« Pourquoi mon clic ne touche pas mon élément ? » — quatre règles :

  1. Ellipse : test de disque réel ((lx/rx)² + (ly/ry)² ≤ 1), pas la boîte englobante. Cliquer un coin vide d'une ellipse ronde ne compte pas.
  2. Rect, texte, bitmap : boîte englobante, rotation et échelle de l'élément inversées avant le test.
  3. Ligne / chemin : boîte englobante des points — le trait fin a une zone cliquable rectangulaire, épaisseur non comprise.
  4. Instance de symbole : l'enveloppe (hull) de tout ce que le symbole dessine, sur toutes ses images, récursivement. Un symbole vide n'est cliquable nulle part. Attention : pour une instance tweenée, le hit-test utilise la position de l'image clé (approximation documentée) — les gros déplacements interpolés peuvent décaler la zone sensible.

Ordre de priorité : les éléments des calques supérieurs gagnent — le hit-test parcourt la liste des nommés à l'envers (dernier dessiné = premier testé).

5.Éditeur vs export : une API, deux machines

Depuis cette session, le contrat est identique des deux côtés : mêmes événements, mêmes portées, mêmes labels, même Scene.onClick. Mais les machines diffèrent — le savoir te fera gagner des heures :

ÉditeurExport HTML
Scripts du documentExécutés au clic sur Exécuter (portée run), rejouablesExécutés une seule fois au chargement (portée run — jamais purgés, ce qui est cohérent : ils ne rejouent pas)
Éléments nommésLes objets de données, brutsDes Proxy qui délèguent play/stop/gotoAndX au MovieClip enfant et le reste à l'élément brut
Subtilité du registreWeakMap keyée par l'élémentWeakMap keyée par l'élément brut (__rawElement) — les proxies sont recréés à chaque collecte, keyer sur eux perdraient les handlers
Porte des événementsstate.playingroot.isPlaying
RenduKonva (canvas + panneau d'outils)Canvas 2D seul, ctx.drawImage etc.
CreateJSChargé par index.html (libs locales)Inliné dans le fichier si et seulement si un script le mentionne

Le réflexe du pont

Chaque fois que tu habilles des objets que tu ne possèdes pas (ici : les données du document, via des Proxy), choisis une seule clé d'identité pour tout ce qui doit leur être attaché (handlers, caches). Ici : l'élément brut. Un Proxy est une vue, jamais une identité.

6.Navigation : labels et images

Dans l'éditeur comme dans l'export :

Scene.gotoAndPlay(0);          // numéro d'image
Scene.gotoAndPlay("Logo");     // label d'image (champ Étiquette de la timeline)
Scene.gotoAndStop("Start");    // idem, en stoppant la lecture

Label introuvable → avertissement console + aucun déplacement (silence volontaire, fidèle à CreateJS). À l'intérieur d'un MovieClip, un script d'image du clip reçoit la même résolution, mais avec les labels du symbole (le champ Étiquette, quand tu édites le symbole).

Patron classique de menu — celui de l'étude de cas : l'image 0 porte le menu, chaque section est une image labellisée, chaque bouton y saute :

Scene.play();
But.on("click", function () { Scene.gotoAndStop("Start"); });
Options.on("click", function () { Scene.gotoAndStop("Options"); });

7.Étude de cas : l'affaire du bouton muet (IIB_v3)

Rejouons l'enquête qui a fait naître les portées — c'est la méthode qui est transférable, plus que le code.

Symptôme

Dans l'app, But.on("click", ...) posé par Exécuter ne réagit jamais. Le quadri-diagnostic dit : createjs object, nommés présents, But object, lecture en cours. Tout est vert — et pourtant rien.

Le raisonnement, étape par étape

  1. Le mécanisme est-il sain ? → Harnais Node : 21 contrôles OK, puis E2E navigateur (dessiner, nommer, exécuter, cliquer) : le clic fonctionne sur une forme ET une instance. Donc le bug est dans la scène du document, pas dans le moteur.
  2. Qu'est-ce que ce document a que mes tests n'ont pas ? → En le lisant ligne par ligne : un calque « action » avec un script d'image (gotoAndPlay("Logo")). C'est la seule différence structurelle.
  3. Quelle interaction ce script a-t-il avec les handlers ? → Relire execCode : il purgeait tous les handlers avant chaque exécution, sans distinction d'origine. Le script d'image s'exécute dès l'arrivée sur l'image 1 — 80 ms après Scene.play() — et efface le handler d'Exécuter.
  4. Reproduire avant de corriger. → Harnais : un handler run + un script d'image → le clic est muet. Corrigé (portées) → 28 contrôles OK. E2E avec le document réel → clic + gotoAndStop("Start") fonctionnent.

Les trois leçons d'enquête à retenir

1. « Ça marche chez moi » ne prouve rien tant que le cas réel n'est pas reproduit. Mes tests étaient sains — et aveugles : aucun n'avait de script d'image. Le document de l'utilisateur était un meilleur test que mes tests.

2. Quand tout est vert et que ça ne marche pas, cherche ce qui est diffèrent chez le client — pas ce qui est cassé chez toi. La diff structurale (un script d'image) était visible en lisant son JSON.

3. La correction d'un bug doit se verrouiller par un test qui échouait avant. La section 13 du harnais échoue sur l'ancien code, passe sur le nouveau : le bug ne pourra pas revenir en silence.

9.Recettes du jeu

Recette A — Bouton de section (le patron IIB)

Scene.play();
But.on("click", function () {
  Scene.gotoAndStop("Start");
});

Recette B — Bouton pressable avec retour visuel

Scene.play();
But.on("mousedown", function () { But.scaleX = 0.95; But.scaleY = 0.95; });
But.on("pressup",   function () { But.scaleX = 1; But.scaleY = 1; });
But.on("click",     function () { Scene.gotoAndStop("Start"); });

Recette C — Tween piloté par bouton (CreateJS)

Scene.play();
Panel.on("click", function () {
  createjs.Tween.get(Panel).to({ x: 300 }, 500, createjs.Ease.quadOut);
});
Panel.on("rollout", function () {
  createjs.Tween.get(Panel).to({ x: 0 }, 300);
});

Le Ticker est mis en pause hors lecture : tes tweens s'arrêtent avec l'éditeur. À l'export, ils vivent leur vie tant que la page tourne (pas de bouton pause).

Recette D — Glisser une instance (dans le cadre)

Scene.play();
let off = null;
But.on("mousedown", (ev) => { off = { dx: But.x - ev.stageX, dy: But.y - ev.stageY }; });
But.on("pressmove", (ev) => {
  if (!off) return;
  But.x = Math.max(0, Math.min(Scene.width,  ev.stageX + off.dx));
  But.y = Math.max(0, Math.min(Scene.height, ev.stageY + off.dy));
});
But.on("pressup", () => { off = null; });

10.Exercices v2

Tous se font dans ton éditeur, puis se valident par export HTML : ce qui doit marcher des deux côtés.

Exercice 1 — Le menu trois boutons

Trois images labellisées (Menu, Jeu, Score) et trois boutons nommés (B1, B2, B3) sur l'image Menu. Chaque bouton saute à sa section ; un bouton « Retour » (présent sur les sections) ramène au Menu. Valide dans l'export.

Indice

Un seul script du document suffit : les trois handlers en top-level. Le bouton Retour peut être le même nom d'instance posé sur chaque image de section — le handler reste valable (les variables sont injectées par image, mais les handlers vivent sur l'élément à chaque collecte... attention : vérifie dans l'export !).

Exercice 2 — Prédire avant de tester

Un calque porte un script d'image à l'image 5 : tst.on("tick", function(){ n++; }); (n étant une variable globale posée par le script du document). Sans exécuter : combien de fois n s'incrémente-t-il par passage sur l'image 5 après trois boucles ? Justifie avec les portées.

Corrigé

Trois. À chaque arrivée sur l'image 5, le script d'image est exécuté en portée 'frame' : la purge retire le handler du passage précédent (même portée), puis en repose un. Toujours exactement un handler actif — c'est précisément ce que les portées garantissent. Sur l'ancien système (sans purge sélective), ce serait 1, 2 puis 3 handlers → 6 incréments au troisième passage.

Exercice 3 — Le clic fantôme

Un utilisateur se plaint : « mon bouton ne réagit qu'une fois sur douze ». Son bouton est une instance nommée Go, sur un calque tweené de l'image 0 à l'image 11. Diagnostique, puis propose LA correction côté scène (pas côté code).

Corrigé

Le hit-test d'une instance tweenée utilise la position de l'image clé (approximation documentée). Selon l'image courante, le bouton dessiné est ailleurs que la zone cliquable — d'où « une fois sur douze » (aux images proches de la position de la clé). Corrections de scène : retirer le tween sur ce calque (bouton statique), ou viser une zone sensible stable. Côté code, on ne peut pas deviner la position interpolée — c'est une limite assumée.
